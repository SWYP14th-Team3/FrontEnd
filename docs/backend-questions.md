# 백엔드 확인 사항 정리

> 프론트엔드 설계 확정을 위해 백엔드 개발자와 의논이 필요한 항목들

---

## 1. 인증 (최우선)

프론트 인증 아키텍처 전체가 이 답변들에 의존합니다.

### 1-1. 토큰 형식

| 질문                                           | 프론트 설계에 미치는 영향                                                                   |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------- |
| JWT인지 opaque 토큰인지?                       | JWT면 프론트에서 만료 시간 디코딩 가능 → 만료 전 선제적 갱신 가능. opaque면 401 응답에 의존 |
| access token만 있는지, refresh token도 있는지? | refresh token이 있으면 자동 갱신 로직 필요. 없으면 만료 시 재로그인                         |

### 1-2. 토큰 전달 방식 (가장 중요)

| 질문                      | 프론트 설계에 미치는 영향                  |
| ------------------------- | ------------------------------------------ |
| 토큰을 어떻게 전달하는지? | **이 하나가 프론트 아키텍처를 결정합니다** |

**경우 A: Set-Cookie (httpOnly 쿠키)**

```
백엔드가 Set-Cookie 헤더로 토큰 전달
→ 브라우저가 이후 모든 요청에 쿠키 자동 포함
→ 프론트에서 토큰 관리 불필요
→ Axios 인터셉터 불필요
→ fetch만으로 충분
```

**경우 B: 응답 바디 / 일반 쿠키**

```
백엔드가 JSON 응답 바디에 토큰 전달
→ 프론트가 토큰을 저장하고 매 요청마다 Authorization 헤더에 직접 부착
→ 401 시 자동 갱신 로직 필요
→ Axios 인터셉터 도입 합리적
```

### 1-3. 토큰 갱신

| 질문                                               | 프론트 설계에 미치는 영향   |
| -------------------------------------------------- | --------------------------- |
| refresh 엔드포인트 URL? (예: `POST /auth/refresh`) | 갱신 로직 구현              |
| refresh token은 어떻게 전달하는지? (쿠키? 바디?)   | 갱신 요청 구성              |
| access token 만료 시간?                            | 갱신 빈도, 선제적 갱신 여부 |

### 1-4. OAuth 플로우

| 질문                          | 프론트 설계에 미치는 영향                                          |
| ----------------------------- | ------------------------------------------------------------------ |
| 카카오 OAuth도 하는지?        | 현재 백엔드 `.env`에 Google만 준비됨. 명세서에는 카카오+구글 둘 다 |
| OAuth 콜백 URL을 누가 받는지? | 아래 상세                                                          |

**OAuth 콜백 URL — 두 가지 방식:**

| 방식                 | 흐름                                                                                                                          | 프론트 영향                                       |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| **A. 백엔드가 받기** | 카카오 → `backend:8080/login/code/kakao?code=xxx` → 백엔드가 토큰 교환 + 쿠키 설정 + 프론트로 리다이렉트                      | Route Handler 불필요. 리다이렉트 결과만 받으면 됨 |
| **B. 프론트가 받기** | 카카오 → `frontend:3000/api/auth/kakao/callback?code=xxx` → 프론트 Route Handler에서 인가 코드 수신 → 백엔드에 토큰 교환 요청 | Route Handler 설계 필요                           |

현재 백엔드 `.env.local.example`:

```
GOOGLE_REDIRECT_URI=http://localhost:8080/login/code/google
```

→ **A 방식(백엔드가 직접 받기)**으로 보이지만 확정 필요.

## 2. API 스키마

프론트 타입 정의와 컴포넌트 설계에 필요합니다.

### 2-1. 분석 결과 응답 구조

| 질문                                                            | 프론트 설계에 미치는 영향                                              |
| --------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 분석 결과 API 응답 JSON 전체 구조?                              | TypeScript 타입 정의, 컴포넌트 props 설계                              |
| 공고 요구사항 ↔ 이력서 섹션 매칭 관계는 어떤 형태로 내려오는지? | 양방향 클릭 매칭(4.4) 구현. 현재 프론트 설계에서는 아래 형태를 가정 중 |

프론트가 가정하는 매칭 데이터 구조 (렌더링 전략 문서 기준):

```json
{
  "matchMap": {
    "jd-requirement-id-1": ["resume-section-id-1", "resume-section-id-2"],
    "jd-requirement-id-2": ["resume-section-id-3"]
  }
}
```

→ 백엔드의 실제 응답 구조와 맞추기 필요

### 2-2. 분석 프로세스

| 질문                                                                    | 프론트 설계에 미치는 영향                               |
| ----------------------------------------------------------------------- | ------------------------------------------------------- |
| 분석 요청 후 진행 상태를 어떻게 알 수 있는지? (SSE / polling / webhook) | 로딩 화면(3.0) 구현 방식 결정                           |
| 분석 완료 여부를 조회하는 엔드포인트?                                   | `/result/[id]` 페이지 진입 시 분기 (로딩 UI vs 결과 UI) |
| 분석 요청 시 즉시 ID가 발급되는지?                                      | 요청 후 `/result/[id]`로 이동 가능 여부                 |

**프론트가 가정하는 흐름:**

```
POST /api/analyze → { analysisId: "abc" } 즉시 응답
→ router.push(`/result/abc`)
→ /result/abc 페이지에서 상태 조회
  → processing이면 로딩 UI (SSE로 진행률 수신)
  → completed면 결과 렌더링
```

### 2-3. 페이지네이션

| 질문                                                          | 프론트 설계에 미치는 영향        |
| ------------------------------------------------------------- | -------------------------------- |
| 페이지네이션 방식? (offset 기반 vs cursor 기반)               | `/history` 페이지네이션 컴포넌트 |
| 응답에 총 개수(totalCount)와 총 페이지(totalPages) 포함 여부? | 페이지 번호 UI 렌더링            |

프론트가 가정하는 형태:

```json
{
  "data": [...],
  "page": 1,
  "totalPages": 5,
  "totalCount": 72
}
```

### 2-4. 공통 응답/에러 형식

| 질문                                                             | 프론트 설계에 미치는 영향     |
| ---------------------------------------------------------------- | ----------------------------- |
| 성공 응답 공통 래퍼? (예: `{ success: true, data: ... }`)        | API 함수에서 응답 파싱        |
| 에러 응답 형식? (예: `{ code: "UNAUTHORIZED", message: "..." }`) | 에러 메시지 추출, 사용자 안내 |

현재 백엔드에 구현된 `ApiResponse<T>` 구조 확인 필요.

## 요약: 우선순위

| 순위  | 항목                                      | 하나만 답해도 프론트가 진행 가능한 것     |
| ----- | ----------------------------------------- | ----------------------------------------- |
| **1** | 토큰 전달 방식 (Set-Cookie vs 바디)       | Axios 도입 여부 + 인증 아키텍처 문서 확정 |
| **2** | OAuth 콜백 URL (백엔드 vs 프론트)         | Route Handler 설계 확정                   |
| **3** | 카카오 OAuth 여부                         | 로그인 모달 UI + OAuth 플로우 확정        |
| **4** | 분석 진행 상태 전달 방식 (SSE vs polling) | 로딩 화면 구현 방식 확정                  |
| **5** | 분석 결과 JSON 구조                       | 타입 정의 + 컴포넌트 구현 시작 가능       |
| **6** | 타임라인                                  | mock 전략 결정                            |
